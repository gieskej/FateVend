## 2026-07-19

### fix: serve.sh's stale-process cleanup was unreliable across shells
**What changed:** The PID-file mechanism added 2026-07-17 (`.serve-static.pid`/`.serve-aidungeon.pid` + `kill`/`taskkill`) still didn't reliably kill stale instances — the actual root cause, diagnosed with the user (who runs `serve.sh` from Cygwin), is that this script gets launched from whatever shell a developer prefers (Cygwin, Git Bash, WSL, ...), and a PID one shell's Python/Node process reports about itself is frequently meaningless in another shell's process namespace: Cygwin ships its own `python3` with Cygwin-space PIDs distinct from native Windows PIDs, so `taskkill //F //PID <pid>` recorded by a Cygwin run could silently no-op (or, worse, coincidentally target an unrelated real Windows process) when read back by Git Bash, and vice versa. Replaced PID files entirely with an HTTP-based self-identification/shutdown handshake, which is inherently shell-agnostic since it never touches OS PID namespaces: `aidungeon-server.mjs` (fixed port 7432) gained a loopback-only `POST /shutdown` route; the static file server (dynamic port starting at 8080) gained matching `GET /__fatevend_ping__` (returns a fixed marker body) and loopback-only `GET /__fatevend_shutdown__` routes. Before starting, `serve.sh` now pings port 7432 and sweeps ports 8080-8109 for that marker, shutting down anything that responds — leaving genuinely unrelated apps on those ports untouched, since they won't answer the marker. Also removed the two now-dead `.serve-*.pid` `.gitignore` entries and the leftover pidfiles on disk.
**Impact:** `serve.sh` can now be started from any shell and reliably stop an instance previously started from a *different* shell — the exact scenario the old mechanism failed at. No more accumulating orphaned dev-server processes across restarts regardless of which terminal you use.
**Test cases:** Manually cleared all running FateVend processes, then: (1) ran `serve.sh` fresh from Git Bash — clean bind to 8080, no stale-instance messages. (2) Ran it again from Git Bash without manual cleanup — correctly detected and stopped both the previous static server and AI Dungeon server, rebound to 8080 (didn't fall back to 8081). (3) Ran it from the user's actual Cygwin shell — correctly stopped the Git-Bash-launched instance. (4) Ran it from Git Bash again — correctly stopped the Cygwin-launched instance, confirming the fix works in both cross-shell directions. Verified via `Get-NetTCPConnection` after each run that exactly one instance of each server was listening, never more. Live Playwright smoke test confirmed the app itself still generates scenarios normally afterward.

### refactor: collapse the two prompt systems onto one shared buildPrompt(skeleton, voice)
**What changed:** FateVend had two parallel, hand-synced prompt systems: the browser (`index.html`) built prompts inline from `GENRE_VOICE` (thin content), while the CLI/module path (`api-client.js` → per-genre `genres/<g>/prompt-template.js` via `PROMPT_TEMPLATES`) used its own richer per-genre `buildPrompt`/`SYSTEM_PROMPT`/`parseResponse`. The 7 `prompt-template.js` files are deleted. Uploaded genre packs (JSON-only, no `outputRules`) fall back to a generic output-rules body built from their `openingNote`/`appearanceNote`, preserving their behavior.
**Impact:** Adding a built-in genre no longer means authoring + hand-syncing two prompt systems — just one `voice.js` + a `GENRE_VOICE` entry. The **live browser app now sends the richer, more genre-distinct system prompts and output rules** it previously only used on the CLI path (directly serves the standing "genres feel factual/boring" goal). One behavior change worth noting: the browser now applies output-length limits (including `authorNote`, previously untruncated on the CLI path) uniformly via `enforceOutputLimits`.

### fix: zipped genre pack lost its icons/audio after a page reload
**What changed:** Importing a `.zip` genre pack built blob: URLs for its bundled `icons/`+`audio/` and persisted the pack to IndexedDB — but the persisted record stored only `{ id, pack }`, **not** the extracted asset Blobs. blob: URLs are per-document and die on refresh, so after a hard reload `loadStoredGenrePacks()` re-registered the pack from IndexedDB with `rec.assets` undefined (`installPackAssets(id, {})` → no blob URLs), and every icon fell back to the pack's own nonexistent `generator/genres/<id>/icons/` path → the whole pack reverted to ⚙ gear placeholders. Now the extracted asset Blobs are stored in the IndexedDB record too (Blobs are structured-cloneable), so on reload the blob: URLs are rebuilt from them. JSON-only packs (no assets) are unaffected.
**Impact:** A zipped pack's icons and BGM now survive page reloads, matching the persistence the data already had. Note: a pack imported *before* this fix was stored without its Blobs — remove and re-import it once to persist the assets.
**Test cases:** Real-browser (Playwright, same context so IndexedDB persists) — imported `example-pirate-cove.zip`, performed a hard reload, and confirmed after reload the pack re-appears and its carousel cover + 8 genre-specific slot icons resolve to `blob:` URLs with **0 gear placeholders, 0 404s, 0 console errors** (before the fix the same reload produced all gears).

### fix: serve.sh left orphaned server processes running across restarts
