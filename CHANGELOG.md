# Changelog

## 2026-09-05

### feat: pick the Ollama model from a list, and show whether each provider URL answers
**What changed:** Two related additions to Settings, both aimed at the same failure: a provider that is misconfigured in a way nothing tells you about until a generation fails minutes later.

**The model field is now a pick list.** Entering an Ollama URL probes `/api/tags` and rebuilds the Model field as a `<select>` of what that server actually has installed. The text input remains the canonical value — everything else (`callOllama`, `localStorage` persistence, seeding from `config.js`) reads `#ollama-model.value`, so the select is a control that writes into that input rather than a replacement for it, and the generation path needed no changes at all.

It degrades to the plain input rather than trapping anyone. A hard select would be a dead end whenever the server is unreachable — a LAN box that is off, a typo, a blocked origin — leaving no way to type a name and no way to reach an already-saved one. Two edge cases are deliberate: a saved model the server no longer reports is kept and listed as `name (not installed)` rather than silently discarded, and an empty field gets a disabled `— choose a model —` placeholder, so typing a URL never auto-adopts whichever model happens to sort first.

**Each URL field gained a reachability lamp** next to its label — Ollama, Stable Diffusion, Kokoro. Each is checked with a cheap GET against the same server the app would really use (`/api/tags`, `/sdapi/v1/sd-models`, `/v1/models`), which makes green mean *this page can talk to it* rather than *something is listening*. That distinction is the whole point: if a server is up but refuses this origin, the app's real calls would fail too, so red is the honest answer and the tooltip says all three possibilities — down, wrong URL, or refusing this page. Probes are debounced 500ms (the field fires per keystroke, and a half-typed host is a request that can only fail) and supersede each other, so a slow unreachable host cannot let a stale verdict land last.

The colors are `--verdigris` and `--rust`, which DESIGN.md already sanctions by name as its two status colors. The glyph inside each lamp (✓ ✕ ·) is not decoration: red-versus-green is precisely the distinction a large share of colorblind readers cannot make, so the state has to survive the color being lost.

**A bug this surfaced, found by testing rather than review:** clearing the URL field left the lamp showing a stale green tick claiming the old server had responded, because `refreshOllamaModels()` returned early on an empty value before reaching the code that resets the lamp. The probe now runs first and owns the reset.

**Impact:** No gameplay change. The specific confusion this removes is real and recent: Ollama's desktop app serves its own UI on a high ephemeral port and answers `/api/tags` with **HTTP 200 and an HTML page**, so a wrong port cannot be diagnosed by status code — only by parsing. Pointed at that port the lamp now goes red immediately and says so, instead of the misconfiguration surfacing later as a JSON parse error during generation.

**Test cases:** All three lamps checked against ground truth established with `curl` first, and they matched: Ollama up (green), Stable Diffusion and Kokoro down (red). Then the reverse, after starting Forge and Kokoro locally — all three green. The state machine was observed with a `MutationObserver` across a real edit: `checking → fail → checking → ok`. The picker was exercised for choosing (writes through to the input and `localStorage`), for a saved-but-uninstalled model (preserved and labelled), and for an empty field (placeholder, no auto-pick). At a 390px viewport horizontal page overflow stays 0.

**The e2e harness needed a fix, and the first attempt at it was wrong.** These probes are optional and environment-dependent, so a contributor without Ollama running would otherwise fail the suite. Exempting them from the `requestfailed` listener was not enough: running with the providers pointed at a dead port gave **58/64**, because Chromium reports a refused fetch *twice* — once through `requestfailed`, and once as a console error whose text carries no URL at all. The exemption is now a shared `isOptionalProbe()` applied to both listeners, matching on the console message's own `location()`. Re-run with every provider unreachable: 64/64. With all three reachable: 64/64.

**Follow-up:** this initially looked like an `INSTALL.md` gap — that `--api` was necessary but not sufficient, and a browser-served page also needed `--cors-allow-origins`. Testing the flag rather than assuming it disproved that; see the CORS entry below for what actually governs this.

### feat: a restore-default control on the LAN provider fields
**What changed:** `Ollama URL`, `Ollama Model`, `Stable Diffusion URL` and `Kokoro URL` each state a default in their placeholder, and there was no way to accept it — the value had to be typed out by hand. Each now carries a small `↺` button that fills it in.

**On the obvious idea, which does not work:** there is no convention by which Enter accepts placeholder text. Enter in a text input means submit; a placeholder is a hint rather than a value, and both MDN and WCAG discourage relying on one to carry information, since it disappears the moment you type. The genuine "accept the suggestion" convention is ghost-text inline completion taken with Tab or →, as in fish, zsh-autosuggestions and browser URL bars — but Tab is already focus navigation inside a form, so binding it would be an accessibility regression. An explicit control avoids all of that and needs no keyboard knowledge to discover.

The default lives in the button's `data-default`, not read back from the placeholder, because Kokoro's placeholder was the template `http://192.168.x.x:8880` — an illustration of a shape, not a value anyone could use. That placeholder is now `http://localhost:8880` so the hint and the button agree, and the tooltip is generated from `data-default` so what a reader is promised cannot drift from what is filled in.

**The load-bearing detail** is that the click dispatches an `input` event. Setting `.value` directly fires nothing, so the existing `KEY_FIELDS` listener would never run: the URL would sit visibly in the box while `localStorage` stayed empty and Ollama stayed disabled in the provider dropdown — indistinguishable from the field being ignored.

**Impact:** Configuration is one click instead of a remembered string, and the wrong-by-default Kokoro hint is gone. No gameplay change.

**Test cases:** All four fill, persist, and (for the URL) flip Ollama from disabled to enabled in the toolbar. Two revisions came out of looking at it rather than reasoning about it: a text `USE DEFAULT` button was 125px and dominated the field, so it became a 2rem icon; and the first version wrapped to its own line at 390px, where it lost the row's stretch and rendered 22px tall — under the 24px WCAG 2.2 target minimum — so the height is now floored. Keyboard activation could not be confirmed through automation, which cannot activate *any* button via synthetic Enter or Space; a throwaway control button established that as a tool limitation rather than a defect, and the control is a native `<button>` with nothing in the page intercepting keys.

### fix: give iOS a home-screen icon instead of a screenshot
**What changed:** Added `web/apple-touch-icon.png` (180×180) and the `<link rel="apple-touch-icon">` that points at it. Noticed while tracing a 404 on the live site: the app ships a `site.webmanifest` with `display: standalone`, so it is meant to be added to a home screen, but had no icon for iOS to use — which falls back to a screenshot of the page.

**The link tag is required, not decorative.** iOS probes for `/apple-touch-icon.png` at the **origin root**, and the app is served from a subpath on GitHub Pages (`/FateVend/`). Shipping the file alone would have changed nothing there; the tag is what makes it resolvable, and it is written relative so it works at both a subpath and a bare root.

The PNG is deliberately opaque and full-bleed, unlike the transparent source art. iOS flattens any transparency onto black and applies its own rounded-corner mask, so the gear is composited onto the app's own ground (`#1a1208`) rather than whatever the platform would pick, and it is left square rather than pre-rounded.

**Impact:** Cosmetic, and only on iOS home-screen installs. Nothing in the page references the icon at runtime.

**Test cases:** Served locally and confirmed the link resolves to a real 200 — 25717 bytes, `image/png`, decoded through `createImageBitmap` as genuinely 180×180 rather than trusted from the filename. Relative resolution checked to be right for the subpath case. `npm test` green — data 8/8 including `icon-files`, e2e 64/64.

**Not done:** `index.html` still has no `<link rel="icon">` or `<link rel="manifest">` at all. `favicon.ico` is only found today because browsers probe the origin root, which is not where this app lives — so the tab icon is likely missing on the hosted demo, and the manifest is never read. Same class of problem, left alone as out of scope here.

### docs: correct what Stable Diffusion actually needs, after testing the flags
**What changed:** `INSTALL.md`'s Stable Diffusion section said to start it with `--api` and nothing more. That is right about `--api` — the `/sdapi/v1/*` routes FateVend calls are off by default — but silent about the cross-origin question, which is the part people lose time to. The section now explains what governs it, and the explanation is not the obvious one.

**`--cors-allow-origins` and `--cors-allow-origins-regex` do nothing.** Both are parsed and then ignored. This was not inferred from reading code: the flag was passed with a literal origin, `sys.argv` was confirmed to contain it, and that exact origin was still refused. The middleware is installed and answering — the preflight comes back 200 with `allow-methods`, `max-age` and `allow-credentials` — it simply never emits `allow-origin`.

What decides it is Gradio's own `CustomCORSMiddleware`, and it keys on **the address you reached the server at**, not on any setting:

```
host_name not in localhost_aliases or origin_name in localhost_aliases
```

Reach Stable Diffusion on a localhost Host and only localhost pages may call it. Reach it on a LAN address and *every* origin may, flag or no flag. So the counterintuitive result is that **a GPU box on another machine is the easier case, not the harder one** — which is why pointing FateVend at a remote server has always just worked with no CORS configuration, while the same-machine setup is the one with a restriction.

**Impact:** The documented failure mode is now the real one. Anyone whose local Stable Diffusion is unreachable should look at `--api`, not at CORS. Also documents the one case no flag can fix: the **hosted demo cannot reach a LAN Stable Diffusion box**, because the demo is HTTPS and browsers block plain-`http://` requests from an HTTPS page. `http://localhost` is exempt as a potentially-trustworthy origin; `http://192.168.1.50` is not. Serving FateVend over `http://` yourself — what `serve.sh` does — avoids it entirely.

**Test cases:** Verified against **two different codebases**, since assuming one explains the other would have been the easy mistake — `stable-diffusion-webui-forge` (classic) on a LAN box, and Forge Neo locally. The rule was isolated by spoofing the `Host` header so the same server could be asked both ways: classic Forge allowed `https://evil.example.com` under `Host: bonobo.local` and refused it under `Host: localhost`; Forge Neo refused a LAN origin under `Host: 127.0.0.1` and allowed it under `Host: 192.168.1.19`. Identical rule in both, so it belongs to Gradio rather than to either Forge generation, and a LAN-reachable instance accepting any origin is its default rather than a local misconfiguration.

**A methodology note worth keeping:** an earlier round of this investigation concluded the opposite, because a CORS flag *appeared* to work — a localhost origin was allowed after passing it. That was the Gradio localhost rule all along; the flag had never reached the process, because `webui.sh` sources `webui.settings.sh`, which hard-sets `COMMANDLINE_ARGS` and discards anything exported from outside. A passing observation that is consistent with the hypothesis is not evidence for it when a second mechanism produces the same result.

### ci: bump the Pages actions off the deprecated Node 20 runtime
**What changed:** The deploy warned that `actions/checkout@v4`, `configure-pages@v5`, `deploy-pages@v4` and `upload-artifact@v4` target Node 20 and were being forced onto Node 24. All four moved to majors that declare `node24` natively — checkout v7, configure-pages v6, upload-pages-artifact v5, deploy-pages v5. The `upload-artifact` in the warning is transitive; `upload-pages-artifact` pulls it in and v5 pins v7.0.0 by SHA.

**One of them was not a drop-in.** `upload-pages-artifact` v4 began excluding dotfiles from the artifact tarball — its v5 source tars with `--exclude=.[^/]*` unless `include-hidden-files` is set, and that input defaults to `"false"`. `web/.nojekyll` is load-bearing here: seven genres ship their carousel icon as `_genre.webp`, and an underscore prefix is exactly what Jekyll strips. A plain version bump would have dropped `.nojekyll` and broken every genre icon on the live site **while the build stayed green**, so the step now passes `include-hidden-files: true`.

The other jumps were checked against this workflow rather than assumed: checkout v6 persists credentials to a separate file, which matters only to workflows that push, and v7 blocks fork-PR checkout for `pull_request_target` and `workflow_run`, while this triggers on `push` and `workflow_dispatch`. configure-pages v6 and deploy-pages v5 are Node 24 bumps with no input changes.

**Impact:** No site change; the deprecation annotation is gone.

**Test cases:** A green check would not have caught a dropped `.nojekyll`, so the deployed site was checked directly rather than the workflow's status. After merge, `.nojekyll` returns 200 and all seven `_genre.webp` icons return 200, with the fantasy and nihongi byte counts (346208 and 35488) identical to the pre-merge baseline — the artifact is equivalent to what v3 produced. The page loads with ~495 requests, all 200; the single 404 is `generator/config.js`, which is gitignored, never committed, guarded by a workflow step that fails the build if it ever appears, and handled by an `onerror` fallback in `index.html`.

## 2026-09-04

### macOS: double-click launcher and app bundle
**What changed:** FateVend already ran on a Mac — `web/serve.sh` worked, and the Node pieces (`aidungeon-server.mjs`, the CLI, the test harness) were already platform-agnostic. What was missing was everything around the app: Windows users double-click `Start-FateVend.cmd` and get a browser, Mac users had to open Terminal and know to type `bash serve.sh`. This closes that gap rather than porting any application code.

Three new files. `Start-FateVend.command` is the direct counterpart to the `.cmd` — Finder runs a `.command` by opening Terminal on it. `FateVend.app` is a real bundle so the launcher has an icon, can live in the Dock, and looks like an application instead of a script; its `Contents/MacOS/FateVend` is a shell script, not a compiled binary, so there is no toolchain, no `npm run build`, and nothing to keep in sync with the web app. `tools/make-mac-icon.sh` regenerates the bundle's `.icns` from `web/android-chrome-512x512.png` via `sips` and `iconutil`, both of which ship with macOS; the committed icon reproduces byte-identically from it, so it isn't an unexplainable binary blob.

The bundle deliberately hands off to Terminal instead of running the server itself. A Finder-launched app has no controlling terminal, and two things depend on having one: the server prints the port it *actually* bound, which is not always `:8080` (it steps forward when taken, and the docs tell people to read that line), and Ctrl+C in that window is how the app gets stopped. Running silently with output going to the system log would take both away. The bundle holds no copy of the game, so it resolves the checkout from its own path and, if it can't find `Start-FateVend.command` next to itself — almost always because it was dragged to `/Applications` alone — raises an `osascript` alert saying so. An alert is the only channel it has; there is no terminal to print to.

**`serve.sh` gained two things.** It now opens a browser, which `serve.ps1` always did and it never did — but only when stdout is a terminal, with `--open` and `--no-browser` to override. The guard is not cosmetic: `deploy/fatevend.service` runs this same script headless under systemd, and `web/tests/e2e/helpers.mjs` spawns it with `stdio: "ignore"`, so a script that always opened a browser would fire one at a server and one per test run. Both cases are non-TTY, so both stay silent, and the double-click path passes `--open` explicitly because Terminal has not attached by the time serve.sh looks.

It also checks for Python 3 before using it. **The docs' claim that macOS "already has" Python 3 was simply false** — `/usr/bin/python3` is a placeholder that does nothing until Apple's Command Line Tools are installed, and invoking it raises a system install dialog that names neither FateVend nor Python as the reason. The check asks `xcode-select -p` instead, which reports the tools' absence *without* triggering that dialog, so a first run that cannot work says so in a sentence naming the one command that fixes it. Every interpreter call in the script now goes through the validated `$PYTHON` rather than bare `python3`.

**Also found and fixed:** `web/serve.sh`, `cli/run.sh` and `deploy/install.sh` were all committed non-executable (mode 644), which is why every instruction in the repo says `bash serve.sh` rather than `./serve.sh`. All three are now `755`.

**Impact:** No gameplay change; nothing in the generator, the data tables or the prompt pipeline was touched. A Mac user's path is now Download ZIP → double-click → playing, matching Windows. Docs were corrected in the same pass: `README.md` and `INSTALL.md` no longer claim a Mac needs nothing, `INSTALL.md` grew real macOS troubleshooting for the two failures a Mac actually hits (Gatekeeper's "unidentified developer" on anything unzipped from a download, and the Command Line Tools prompt), and the Level 2–4 instructions that said "restart `Start-FateVend.cmd`" or "check the black window" now say "the launcher" and "the console window", since a Mac reader had no such thing.

**Test cases:** Verified through the real Finder path, not just by reading the scripts — `open FateVend.app` brought up Terminal, the static server answered `/__fatevend_ping__` with `fatevend-static` on `:8080` within a second, the AI Dungeon import server answered `:7432/ping` with `{"ok":true,"version":1}`, the browser opened on its own, and the app rendered the genre carousel with an empty console. Both servers then shut down cleanly over their own HTTP shutdown routes. The bundle's two branches were exercised separately with `open` and `osascript` stubbed on `PATH`: in place it invokes `open -a Terminal <repo>/Start-FateVend.command`, and copied elsewhere it takes the alert branch and exits 1. The alert's AppleScript was compile-checked with `osacompile` in the literal `\n` form the file actually stores, since AppleScript string escapes are easy to get wrong and the failure would only appear at the moment someone is already confused. `serve.sh --bogus` exits 2 with usage. `npm test` green — data 8/8, e2e 64/64 (settings-modal 8/8, mobile 17/17), with the e2e suite spawning the modified `serve.sh` and opening no browser windows, which is the TTY guard working.

**Not done, deliberately:** the bundle is unsigned and un-notarized, so the first launch from a downloaded ZIP is refused until the user right-clicks → Open. Signing needs a paid Apple Developer account, so this is documented in `INSTALL.md` rather than solved. `icon_512x512@2x` (1024px) is absent from the `.icns` because the largest artwork in the repo is 512px and an upscale would look worse than letting Finder scale.

## 2026-08-09

### security: restrict the AI Dungeon import server to trusted origins
**What changed:** `web/tools/aidungeon-server.mjs` sent `Access-Control-Allow-Origin: *` and `POST /import` performed no origin check at all — it validated the JSON shape and nothing else. Since that route spawns a Playwright browser that logs in with `AIDUNGEON_EMAIL`/`AIDUNGEON_PASSWORD` from `.env`, **any web page the user had open could drive their AI Dungeon account**: `GET /ping` to fingerprint them as a FateVend user, then `POST /import` to act as them. Binding `127.0.0.1` was not protection, because the attacker is not on the network — it is a tab in the user's own browser.

Now only the user's own machine and their own network are trusted, with an explicit opt-in for anything else via `AIDUNGEON_ALLOWED_ORIGINS`. That covers loopback, all of RFC1918 (10/8, 172.16/12, 192.168/16 — complete ranges, not one subnet), link-local/APIPA, CGNAT (100.64/10, which is what Tailscale hands out), IPv6 unique-local and link-local, bare dotless hostnames like `http://desktop:8080` that cannot be public because they have no TLD, and the `.local` / `.lan` / `.internal` / `.home.arpa` suffixes routers assign. Two earlier drafts were too narrow and would have broken contributors on ordinary home networks — the first was loopback-only, which silently hid the button for anyone opening the app from a phone on the LAN (`serve.sh` binds `0.0.0.0` specifically to allow that); the second still missed IPv6-only networks, Tailscale, and Windows-style bare hostnames.

The host check is written as parsing rather than one large regex, because the interesting cases are numeric ranges with real boundaries: 172.16–31 is private while 172.15 and 172.32 are public internet, and a regex that gets that subtly wrong fails open. The specific origin is echoed instead of `*`, and only when allowed, so a disallowed page cannot read *any* response — closing the `/ping` fingerprinting vector too. The startup banner now prints which origins are accepted, since a user should be able to see what may act on their account without reading source.

**The non-obvious half:** rejecting the CORS preflight is not sufficient. A cross-origin `POST` with a safelisted `Content-Type: text/plain` skips preflight entirely, and `JSON.parse` accepts the body regardless — the attacker never needs to read the reply, because the import has already happened. So state-changing routes re-check `Origin` on the real request, not just on `OPTIONS`.

**How it surfaced:** the user opened the hosted GitHub Pages demo and found the Import button live, then watched it log into AI Dungeon as them. Their first fear was that credentials had been published; they had not been — verified that `generator/config.js` and `.env` both 404 on the live site, that `serve.sh`'s only `AIDUNGEON` references are a shell variable holding a PID, and that the live `index.html`'s four matches are help text naming the variables. The hosted page had simply reached a server already running on their own machine.

**A correction:** this repo's own help panel claimed auto-import "is not available on the hosted demo — a page served over HTTPS can't reach a server on your own machine." That is false, and the user's test disproved it. Browsers treat `localhost` as a *potentially trustworthy* origin, so it is exempt from mixed-content blocking, and Private Network Access preflighting has been repeatedly delayed. The help text now says the restriction is enforced deliberately, and documents the opt-in for self-hosted copies.

**Test cases:** Four attacks run against the running server, all now refused where all four previously succeeded — hostile-origin preflight (403), preflight-skipping `text/plain` POST (403, the real bypass), cross-origin `/ping` (no `Access-Control-Allow-Origin` header at all, so unreadable), and the GitHub Pages origin (403 by default). Then 26 origins checked against the widened rules: 16 home/dev network forms all allowed (seven different 192.168 subnets, 10/8, 172.20, Tailscale-range, APIPA, `desktop`, `raspberrypi`, `nas.lan`, `box.home.arpa`, `srv.internal`, `bonobo.local`, IPv6 ULA/link-local/`[::1]`), and 10 public forms all refused — including the boundary cases that a sloppy range check gets wrong (`172.15`, `172.32`, `100.63`, `100.128`) and suffix-spoofing attempts (`192.168.1.1.evil.com`, `x.local.evil.com`). Confirmed the local app is unaffected: preflight from `http://localhost:8080` returns 204, `/ping` echoes that exact origin, and `checkImportServer()` flips the button to visible in a real browser. Confirmed the opt-in works: with `AIDUNGEON_ALLOWED_ORIGINS="https://gieskej.github.io"` the demo is permitted while `evil.example` stays refused. `npm test` green — data 8/8, e2e 64/64.

**Note on the button's visibility:** it appears only after a full AI generation, because it is part of the rendered output and `checkImportServer()` is called once, right after `renderOutput()`. Spinning the reels alone never shows it. That is pre-existing behaviour, not a consequence of this change — worth recording because it reads exactly like the origin check failing.

### fix: keep the current phase visible in the status bar on mobile
**What changed:** `#status-bar` used `overflow: hidden` + `text-overflow: ellipsis`, which clips at the **right** — precisely where the active phase sits, since the strip is one nowrap line that fills left to right and the active phase moves rightward as generation proceeds. So on a narrow screen the one phase actually worth reading was the one replaced by "…". It now scrolls horizontally (scrollbar hidden — it scrolls itself, it isn't a control), and `setPhase()` scrolls the active phase into view after each update, pushing *finished* phases off the left instead. Measured with `getBoundingClientRect` rather than `offsetLeft`, because the spans' `offsetParent` isn't necessarily the container. It self-limits to the overflow case, so no media query is needed and wide screens are untouched.
**Impact:** The phase in progress is always fully readable; completed phases scroll away as history rather than crowding it out.
**Test cases:** Verifying this took several attempts worth recording. At 390px the strip does overflow (99–113px past the slot), but for the phases reachable from a plain reel spin — Rolling Stats / Personality / Fate — the *active* one still happened to fit, so the new code never fired and proved nothing. The late phases (Narrative, Portrait, NPC Portraits), which are what the report was about, are only reachable through `runAIPhase()`, i.e. a billed generation; an attempt to reach it with the provider endpoints blocked failed fast and cleared the strip before it could be sampled. The scroll path was finally exercised by narrowing the viewport until an early phase genuinely overflowed — the logic is width-independent — giving `scrollLeft` 52 at 240px and 37/92 at 200px, with the active phase fully visible in every case. Those offsets are the proof: 92px of content had to move off-screen for the current phase to fit, and that 92px was previously the part being ellipsed. Sampling used a `MutationObserver` with a settle delay rather than polling, since the scroll is smooth-animated. `npm test` green — data 8/8, e2e 64/64 including mobile 17/17.
**Follow-up — dead CSS removed (user confirmed the fix works on a real device first):** deleted the whole phase-pipeline block that the earlier pass had only flagged: `.phase-pipeline`, `.phase-step` and its `+ .phase-step::before` connector, `.active`/`.done` variants, `.phase-dot` with its two state rules, the `pulse-dot` keyframes those were the sole user of, and the mobile `.phase-step span { display: none }` override. 68 lines out, 19 in (a comment recording what was there and why it went). Nothing rendered any of it — `setPhase()` writes plain spans into `#status-bar` — and the `phase-*` strings that do appear in JS are `BASE_PHASES` data keys, not DOM ids or classes, which was checked before deleting. The mobile `display: none` rule was the reason to remove rather than leave it: it read as load-bearing for the status bar it no longer had any connection to.

Verified after removal at both viewports: status bar still renders and animates, no console errors, mobile horizontal overflow still 0px, `npm test` green (data 8/8, e2e 64/64, mobile 17/17, settings-modal 8/8).

**Found, pre-existing, not addressed:** desktop at 1280px has **80px of horizontal page overflow**. Confirmed unrelated to this change by stashing it and re-measuring — identical 80px with the dead CSS restored. The e2e mobile suite asserts no horizontal overflow; nothing makes that assertion for desktop.

### fix: wrap multi-word sheet labels on mobile
**What changed:** In the Rolled Character Sheet at a 390px viewport, a label like "BACKGROUND TENSION" held its column open at its full single-line width — **210px of a 390px screen, leaving the value 67px**, roughly two words per line. `.skeleton-key` now takes a fixed `flex: 0 0 128px` basis inside the existing `max-width: 600px` block, with `.skeleton-row` set to `flex-wrap: nowrap`.
**Impact:** Every value column is a consistent **150px instead of 67px** at the worst row, and "PLOT ARCHETYPE" / "BACKGROUND TENSION" wrap to two lines. Desktop is untouched.
**Why not the obvious fixes:** `flex-shrink: 1` alone doesn't work — shrinkage is distributed in proportion to base size, and the value's base (its whole unwrapped paragraph) dwarfs the label's, so the value collapsed to its longest word while the label barely moved (210 → 196px). ### perf: get the CDNs and the icon preload off the critical path
**What changed:** Three fixes, found by profiling the real page in Chromium rather than by inspection.
1. **JSZip is no longer loaded up front.** It was a synchronous `<script>` on jsdelivr in `index.html`'s `<head>`, so every page load blocked first paint on a third-party CDN — despite JSZip only being needed for genre-pack import/export, a rare user-initiated action. `app.js` now has `ensureJSZip()`, which injects the script on first use and caches the promise so concurrent callers share one insertion; a failed fetch clears the cache so a transient network error doesn't disable zip support for the whole session. Both call sites already guarded on `typeof JSZip === "undefined"`, so they simply `await` it now. `downloadPackage()` keeps the library-fetch failure in its own try block, so "couldn't download the library" doesn't render as the same opaque "Error" button as a genuine build failure.
2. **The Google Fonts stylesheet no longer blocks rendering.** Loaded as `media="print"` and promoted to `all` on load, with a `<noscript>` fallback. The fonts already requested `display=swap`, so text was always going to appear in a fallback face first — this just stops the rest of the page waiting on the CDN too.
3. **`serve.sh` sends `Cache-Control: no-cache` instead of `no-store`.** Both guarantee you never see a stale icon, but `no-store` forbade the browser from keeping a copy at all, so every reload re-sent ~3.8MB across ~220 icon requests. `no-cache` still forces revalidation on every use — verified `SimpleHTTPRequestHandler` answers `If-Modified-Since` with a 0-byte 304 — so an edited file still updates immediately while an unchanged one costs a conditional request instead of its body.
4. **The startup icon preload is deferred to after `load`,** via a new `whenIdleAfterLoad()` helper (`requestIdleCallback` with a `setTimeout` fallback for Safari). It still fetches the same ~220 images; they just no longer compete with the app's own scripts and styles. The helper also caps its wait at 5s rather than only listening for `load`, because `load` waits on third-party subresources — a hung font CDN would otherwise mean the preload silently never ran at all.

### fix: serve.sh's stale-process cleanup was unreliable across shells
**What changed:** The PID-file mechanism added 2026-07-17 (`.serve-static.pid`/`.serve-aidungeon.pid` + `kill`/`taskkill`) still didn't reliably kill stale instances — the actual root cause, diagnosed with the user (who runs `serve.sh` from Cygwin), is that this script gets launched from whatever shell a developer prefers (Cygwin, Git Bash, WSL, ...), and a PID one shell's Python/Node process reports about itself is frequently meaningless in another shell's process namespace: Cygwin ships its own `python3` with Cygwin-space PIDs distinct from native Windows PIDs, so `taskkill //F //PID <pid>` recorded by a Cygwin run could silently no-op (or, worse, coincidentally target an unrelated real Windows process) when read back by Git Bash, and vice versa. Replaced PID files entirely with an HTTP-based self-identification/shutdown handshake, which is inherently shell-agnostic since it never touches OS PID namespaces: `aidungeon-server.mjs` (fixed port 7432) gained a loopback-only `POST /shutdown` route; the static file server (dynamic port starting at 8080) gained matching `GET /__fatevend_ping__` (returns a fixed marker body) and loopback-only `GET /__fatevend_shutdown__` routes. Before starting, `serve.sh` now pings port 7432 and sweeps ports 8080-8109 for that marker, shutting down anything that responds — leaving genuinely unrelated apps on those ports untouched, since they won't answer the marker. Also removed the two now-dead `.serve-*.pid` `.gitignore` entries and the leftover pidfiles on disk.
**Impact:** `serve.sh` can now be started from any shell and reliably stop an instance previously started from a *different* shell — the exact scenario the old mechanism failed at. No more accumulating orphaned dev-server processes across restarts regardless of which terminal you use.
**Test cases:** Manually cleared all running FateVend processes, then: (1) ran `serve.sh` fresh from Git Bash — clean bind to 8080, no stale-instance messages.
